## Context

现有系统以 FastAPI、SQLAlchemy 和 PostgreSQL 实现会员、卡项、交易、核销、审计及时间线，Nuxt 页面中的团课和预约仍由 Mock BFF 提供。核销服务已经支持预扣、签到、取消和缺勤四种事件，但缺少承载 `business_ref` 的真实预约，也没有容量、时间冲突和预约窗口控制。现有账号表只保存用户名与角色，会员令牌无法关联会员资源。

本变更跨越认证、基础资料、排课、预约、核销和前端多个模块，必须继续遵守服务端权限隔离、PostgreSQL 事务一致性、强制幂等和完整审计约束。

## Goals / Non-Goals

**Goals:**

- 提供可运营的真实周课表和复制上周能力。
- 同时支持管理员代约与会员自助预约。
- 将预约生命周期原子地接入现有核销事件链。
- 在并发场景下防止超卖、重复预约、时间冲突和重复终态。
- 支持管理员及任课教练签到，管理员批量结课处理缺勤。
- 为会员提供正式密码账号并绑定资源身份。
- 保持所有关键动作可审计、可追踪、可压测。

**Non-Goals:**

- 候补和自动递补。
- 二维码签到、短信或微信通知。
- 私教时段与私教预约。
- 报表聚合与 Excel 导出。
- 定时自动结课；首期由管理员显式结课。
- 手机验证码登录。

## Decisions

### 1. 使用独立课次与预约实体承载核销业务引用

新增 `Course`、`Room`、`CoachProfile`、`ClassSession` 和 `ClassBooking`。预约 ID 作为稳定 `business_ref`，核销事件仍由现有 `WriteOffService` 创建，不复制卡项扣返规则。相比直接把课程信息塞入核销事件，该方案保留课程业务状态并使核销继续保持通用。

### 2. 课次状态持久化，满员状态派生

课次持久状态为 `draft/published/paused/cancelled/completed`；`full` 根据有效预约数与容量派生。这样避免取消预约后忘记把 `full` 改回 `published`。课次必须发布后才允许预约。

### 3. 预约终态与核销终态一一对应

`reserved` 创建 `reserve_hold`；`checked_in` 创建 `checkin_commit`；`cancelled` 创建 `cancel_refund`；`absent` 创建 `absence_commit`。所有变更由 `BookingService` 在同一会话事务内协调，任一步失败都回滚预约和权益。

### 4. 使用数据库行锁保证容量和时间冲突

预约时锁定会员与课次行，随后检查有效预约数及重叠课次。课次行锁串行化最后名额竞争，会员行锁串行化同一会员并发约课。数据库增加预约唯一约束和常用查询索引；继续不引入 Redis。

### 5. 复制上周只复制排课，不复制预约

复制操作以源周和目标周为输入，按七天偏移生成 `draft` 课次，保留课程、教练、教室、时段、容量和规则。目标时段冲突的课次跳过并返回冲突详情，避免隐式覆盖运营数据。

### 6. 扩展现有账号表而非立即重命名

为 `admin_user` 增加可空且唯一的 `member_id` 和 `coach_profile_id`。登录时将关联 ID 写入 JWT。该方案兼容已有管理员/教练账号和部署数据，后续可单独迁移为通用账号表。管理员通过会员页面设置用户名和初始密码；接口不回传密码。

### 7. 取消课次和批量结课采用显式批处理

取消课次时锁定全部有效预约并逐条执行取消终态；结课时将未签到预约逐条标记缺勤。每条预约有独立幂等 scope，整个请求在单事务中成功或失败。首期不依赖后台调度，便于故障恢复和验收。

### 8. 前端按角色提供不同入口

管理员使用基础资料页、周课表和独立课次运营页；会员使用角色化周课表和“我的预约”；教练通过周课表查看本人课次，并进入独立运营页查看名单和签到。管理员分别在会员与教练列表开通账号。前端守卫只改善体验，所有资源归属仍由后端验证。

### 9. 预约窗口使用相对课前时长

课次保存预约提前开放小时数、课前停止预约分钟数和课前停止取消分钟数，不保存绝对截止时间。接口按课次开始时间派生实际窗口，使复制上周时规则可原样复用。课程封面首期仅保存可空 URL，不引入上传或对象存储能力。

### 10. 取消后允许重新预约

同一会员取消预约后，只要仍在预约窗口内且课次有余位即可重新预约。数据库仅对 `reserved` 状态建立 `(class_session_id, member_id)` 部分唯一索引，每次预约保留独立 ID 和核销历史。

### 11. 幂等键覆盖关键业务写操作

预约、取消预约、签到、完成课次、取消课次、复制周和会员开户强制要求 `Idempotency-Key`。普通课程、教室和教练资料 CRUD 不强制幂等键；其重复与并发由唯一约束和资源版本校验处理。

### 12. 基础资料读取与周课表投影

课程、教室和教练资料允许所有已登录角色读取，写操作仅管理员可用。周课表响应除稳定 ID 外直接提供课程、教练和教室名称，避免前端为每个课次额外拼装基础资料。

### 13. 复制范围与完成条件

复制周使用除 `cancelled` 外的全部源课次作为模板，目标课次统一创建为 `draft`。课次仅能在 `end_at` 到达后完成；Task 2 阶段若仍有有效预约则拒绝取消或完成，Task 4 再扩展为批量终结预约权益。

### 14. 会员与教练账号均采用管理员开户

管理员分别为会员和教练档案设置用户名及初始密码。会员 JWT 包含 `memberId`，教练 JWT 包含 `coachProfileId`；禁用或删除会员、停用教练不得登录。停卡和到期会员可以登录查看历史，但预约资格仍要求会员状态正常。

### 15. 预约窗口、签到和馆方取消

会员预约遵守课次相对开放和截止时间，管理员代约可绕过时间窗口但不能绕过容量、会员状态、时间冲突和卡项资格。签到从课前 30 分钟开始，课次完成前允许补录。会员或管理员取消单笔预约时遵守卡项取消规则；馆方取消整节课时强制返还所有预扣权益，且已有签到记录时拒绝取消课次。

## Risks / Trade-offs

- [批量取消或结课对大课次持锁时间较长] → 首期容量以瑜伽馆常见规模为限，并对单课容量设合理上限；集成测试覆盖事务回滚。
- [现有 `specific_course_ids` 是 JSON，缺少外键] → 写入卡项时校验课程存在，预约时再次校验；后续可迁移关联表。
- [现有账号表命名为 `admin_user`] → 暂时只扩展字段保持兼容，在后续认证专项中重命名。
- [管理员手动结课可能遗漏] → 周课表突出“待结课”状态并提供筛选；自动调度留给后续变更。
- [复制上周可能产生教练或教室冲突] → 创建前检测，冲突项不写入并在响应中明确返回。

## Migration Plan

1. 先部署新增表和账号关联字段，保留所有现有 API。
2. 部署基础资料、排课、预约和账号 API。
3. 创建课程、教室及教练基础数据后启用真实课表页面。
4. 将现有卡项的指定课程 ID 人工映射到真实课程 ID。
5. 验证预约、取消、签到、缺勤和时间线后移除团课相关 Mock BFF。
6. 回滚时先恢复前端 Mock 路由，再回滚应用；新增表保留以避免业务数据丢失。
